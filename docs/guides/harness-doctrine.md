# 하니스(Harness) 독트린 — 모델보다 중요한 주변 시스템

> **대상**: Alien Agentic 전 직원 — 기영님 + 27명의 외계 에이전트
> **목적**: "왜 우리가 새 모델을 기다리지 않고, *모델 옆 시스템*에 시간을 쓰는가" 를 한 페이지로 합의한다.
> **한 줄 결론**: **모델은 천장이다. 하니스는 사다리다.** 같은 모델로도 결과는 46점 ~ 80점까지 벌어진다. 그 34점을 결정하는 것이 하니스다.

---

## 1. 핵심 사실 — 숫자로 먼저

| 사실 | 출처 / 일화 | 우리에게 주는 메시지 |
|---|---|---|
| 같은 클로드 모델, 같은 벤치마크 — **46점 vs 80점** (34점 차) | 커서(Cursor) 실험 | 모델이 천장이지만, 하니스가 사다리다 |
| 하니스 정비 시 결과물 품질 **+28% ~ +47%** | 스탠포드 연구 | 28% 이상의 ROI가 거의 보장된 영역 |
| 프롬프트만 다듬을 때 품질 향상 **3% 미만** | 동일 연구 | 프롬프트 튜닝은 디저트, 하니스는 본식 |
| 에반이 작년 6월, **소형 Sonnet 모델 + 잘 짜인 하니스**로 대규모 마이그레이션을 *반나절*에, 버그 1개만으로 끝냄 | 에반 실전 사례 | 모델 등급보다 *모델을 둘러싼 시스템*이 결과를 정한다 |

> 비유: F1 드라이버가 아무리 뛰어나도, **경운기**를 주느냐 **레이싱카**를 주느냐가 결과를 정한다. 모델은 드라이버, 하니스는 차다.

---

## 2. 하니스(Harness)란 무엇인가

**정의**: AI 모델이라는 *똑똑한 신입 사원* 옆에 깔아두는 회사의 시스템 일체.
*온보딩 문서 · 매뉴얼 · 자동 검사기 · 메모리 · 작업 명세 · 권한 체계 · 개입 기록* 같은 주변 장치.

### 하니스의 11가지 요소

| # | 요소 | 한 줄 설명 |
|---|---|---|
| 1 | **작업 명세 (Spec)** | "무엇을 / 왜 / 어떻게 끝났음을 어떻게 아는가" 를 글로 박는다 |
| 2 | **컨텍스트 선택 (Context Curation)** | 모델에게 무엇을 *보여줄지* / *숨길지* 결정한다 |
| 3 | **도구 접근 (Tool Access)** | 모델이 어떤 명령·API·파일에 손을 댈 수 있는가 |
| 4 | **프로젝트 메모리 (Project Memory)** | 어제의 결정·실패·학습이 오늘 자동 로드된다 |
| 5 | **작업 상태 (Task State)** | 지금 어디까지 됐고, 다음 한 걸음이 무엇인지 |
| 6 | **관찰성 (Observability)** | 무엇이 일어났는지 *나중에* 추적할 수 있는가 |
| 7 | **실패 분석 (Failure Analysis)** | 실패가 *왜* 일어났는지 구조적으로 분리 |
| 8 | **검증 (Validation)** | 빌드·테스트·린트가 *사람보다 먼저* 거른다 |
| 9 | **권한 (Permissions)** | 무엇은 모델이 직접, 무엇은 사람 결재가 필요한가 |
| 10 | **엔트로피 감사 (Entropy Audit)** | 코드·문서가 *엉망이 되는 속도* 를 점검한다 |
| 11 | **개입 기록 (Intervention Log)** | 사람이 끼어든 순간을 누락 없이 보관한다 |

**핵심 메시지**: *모델은 11개 중 하나일 뿐*. 나머지 10개를 어떻게 짜느냐가 결과의 전부를 정한다.

## 3. 반나절 마이그레이션을 가능하게 한 3가지 장치

에반의 실전 사례에서, 결정적이었던 하니스 3종은 다음과 같다.

### ① 스펙 리뷰 (Spec Review)
- AI에게 *바로 코드를 고치라*고 던지지 않는다.
- 먼저 **"어떻게 고칠 것인지" 계획서**를 마크다운으로 쓰게 한다.
- 사람이 그 계획서를 검토한 *후에야* 실제 변경에 착수.
- **효과**: 잘못된 방향으로 5시간 달리지 않는다.

### ② 표준 워크플로우 (Workflow)
매 작업이 동일한 순서를 통과:

```
파일 읽기 → 변경 → 테스트 → 커밋
```

- 매번 같은 흐름이라 **병목이 바로 보인다**.
- 어느 단계에서 막혔는지 즉시 파악 가능.

### ③ 자동 검사 (Validation)
- 빌드가 깨지면 *즉시* 신호.
- 사람이 일일이 검수하기 *전에* 자동 검사기가 1차 필터.

## 4. 지속 가능한 하니스를 위한 2가지 축

### ① 스킬(Skill) 기반 리팩토링

| 함정 | 해법 |
|---|---|
| AI에게 매번 "알아서 리팩토링해" 하면 그날 기분에 따라 결과가 들쭉날쭉 | 자주 쓰는 리팩토링 패턴을 **"스킬" = 레시피 카드** 단위로 문서화 |

- 좋은 프롬프트와 규칙은 **멀티턴으로 다듬은 뒤 스킬로 고정**한다.
- 그 순간부터 그 스킬은 *일정한 맛을 내는 자산*이 된다.

### ② 도메인(Domain) 기반 유지보수

| 함정 | 해법 |
|---|---|
| 파일 종류별(MVC: model / view / controller)로 묶으면, 비즈니스 변경이 와도 *어디를 고쳐야 할지* 파편화됨 | **비즈니스 도메인 단위로 코드를 묶는다** |

- 각 도메인 폴더 안에 **"도메인 규칙 매뉴얼"** 을 짧게라도 함께 둔다.
- AI는 그 매뉴얼을 *반복해서 학습*하며 도메인 일관성을 유지.

## 5. 실전 행동 가이드 — 우리가 지금 해야 할 4가지

| # | 행동 | Alien Agentic 적용 |
|---|---|---|
| **1** | **스펙 리뷰 도입** — AI에게 일 시키기 전 *마크다운 작업 계획서* 부터 쓰게 하고 검토 | WHY → HOW → WHAT 깔때기와 동일한 철학. *플랜 먼저, 코드 나중* |
| **2** | **자주 하는 작업을 스킬로 자산화** — 좋은 프롬프트는 멀티턴으로 다듬은 뒤 *고정* | 27명 각자의 시스템 프롬프트 + `prompt-engineer`가 관리하는 스킬 카탈로그 |
| **3** | **코드를 도메인 단위로 묶기** — 새 기능부터 도메인 폴더 + *짧은 규칙 매뉴얼* 동반 | `clients/{client}/WHY/`, `HOW/`, `WHAT/` 구조가 이미 도메인 기반. 폴더마다 README 매뉴얼을 짧게라도 강제 |
| **4** | **자동 검사 시스템** — AI 산출물을 사람이 검수하기 *전에* 빌드·테스트·린트로 1차 필터 | `qa-tester`, `brand-keeper`가 자동 검사 역할. CI 자동화 확장이 다음 과제 |

## 6. Alien Agentic 자기 진단 — 우리 하니스는 지금 어디 있는가

11가지 요소 기준으로 우리의 현재 상태를 정직하게 본다.

| 요소 | 우리 상태 | 보완 자리 |
|---|---|---|
| 1. 작업 명세 | 🟢 Multica 이슈 + WHY/HOW/WHAT 깔때기로 강제 | — |
| 2. 컨텍스트 선택 | 🟡 CLAUDE.md 자동 로드 + CONSTITUTION 수동 | 에이전트별 컨텍스트 큐레이션 미세조정 필요 |
| 3. 도구 접근 | 🟢 `aa` CLI + multica CLI + Claude Code 도구 | — |
| 4. 프로젝트 메모리 | 🟢 shared-memory/agents/{name}/4파일 구조 | 검색·인덱싱 자동화 부재 |
| 5. 작업 상태 | 🟢 Multica 이슈 + `shared-memory/tasks/` Kanban | 두 채널 동기화 자동화 필요 |
| 6. 관찰성 | 🟡 `aa usage` 로그 + daily-logs | 대시보드 시각화 미흡 |
| 7. 실패 분석 | 🟡 `shared-memory/agents/{name}/mistakes.md` 존재 | 패턴 추출 자동화 부재 |
| 8. 검증 | 🟡 `qa-tester`, `brand-keeper` 호출형 | 자동 트리거(CI) 부재 |
| 9. 권한 | 🟢 헌법(CONSTITUTION) + CLAUDE.md 자동 보호 트리거 | — |
| 10. 엔트로피 감사 | 🔴 명시적 절차 없음 | **다음 과제** — 정기 코드/문서 엔트로피 점검 루틴 도입 |
| 11. 개입 기록 | 🟢 `shared-memory/interventions/` 폴더 + 처리 우선순위 룰 | — |

**다음 90일 보강 우선순위**: ⑩ 엔트로피 감사 → ⑧ 검증 자동화 → ⑥ 관찰성 대시보드.

## 7. 27명 외계 동료가 지킬 4개 원칙 — 매 호출 적용

각 에이전트는 호출될 때 다음 4가지를 *자동으로* 지킨다.

1. **계획 먼저, 실행 나중** — 5줄 이상의 작업은 *어떻게 할 것인지* 를 먼저 쓰고 시작한다.
2. **자기 스킬 명시** — 반복되는 패턴은 *내 work.md*에 *스킬*로 기록해 다음 세션이 재사용하게 한다.
3. **도메인 매뉴얼 갱신 의무** — 작업한 도메인 폴더의 README/매뉴얼을 *변경에 맞춰* 갱신.
4. **실패 기록 의무** — *실패 1건은 자산 1건이다.* `mistakes.md` 에 *왜 / 무엇이 / 어떻게*를 남긴다.

## 8. 에반의 최종 고백 — 우리 회사 언어로

> *"모델은 천장이지만, 하니스는 사다리입니다."*

새 모델이 나오길 기다리며 시간을 쓰기보다,
**지금 쓰는 모델 옆에 스킬 한 줄, 매뉴얼 한 줄, 검사기 한 줄**을 깔아두는 것이
일의 효율을 *2배 이상* 바꾼다.

이것이 Alien Agentic이 *외계의 효율*이라고 부르는 것의 실체다.
새로운 마법을 기다리지 않고, **지금 자리에 사다리 한 칸을 더 올린다.**
